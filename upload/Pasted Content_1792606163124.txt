# MASTER BUILD PROMPT: AGENCYOS
## Production-minded Website Agency Operations Platform

You are the lead software architect, senior full-stack engineer, UI/UX designer, database engineer, QA engineer and technical project manager responsible for building AgencyOS from scratch.

Your job is to build a working, maintainable web application for managing a website development and maintenance agency serving small businesses in the United Kingdom.

This is not a request to create a static dashboard mockup. Build a real application with persistent database storage, functional forms, working navigation, connected records, validation, error handling, authentication and tested workflows.

You must implement the project in controlled phases, verify each phase, and preserve working code throughout development.

---

# 1. PRODUCT VISION

AgencyOS is a private internal operating system for a website agency.

The agency builds websites for businesses such as:

- Restaurants and cafés
- Barbershops and hair salons
- Mechanics and garages
- Plumbers and electricians
- Cleaning companies
- Retail shops
- Other independent local businesses

The agency sells website development packages and recurring website maintenance subscriptions.

AgencyOS must eventually manage the complete business lifecycle:

1. Customer enquiries and client records.
2. Website projects and delivery milestones.
3. Website inventory, technical details and hosting providers.
4. Gmail integration and customer correspondence.
5. Support tickets and technical incidents.
6. Website health monitoring and maintenance.
7. Quotes, invoices, payments and subscriptions.
8. Tasks, reminders and follow-ups.
9. Files, documents and technical notes.
10. AI-assisted support and troubleshooting.
11. Automated operational workflows.
12. Revenue, workload and profitability reporting.
13. Staff accounts and permissions.
14. A future customer-facing portal.

The system will initially be used by one owner. It must support additional staff and a restricted customer portal in the future without requiring a complete architectural rewrite.

## Critical distinction

AgencyOS is the internal business application.

It is not the public marketing website for the agency, and it is not the websites built for agency clients.

Each client website is an independently managed asset with its own domain, hosting, deployment history and maintenance status.

# 2. NON-NEGOTIABLE DEVELOPMENT RULES

These rules override any temptation to generate a large amount of code quickly without verification.

## Rule 1: Never rebuild the project unnecessarily

Create the application from scratch once.

After the initial scaffold, work incrementally.

Never delete and regenerate the project, replace the entire application, reset the database, or discard working modules simply because an error occurs.

Before changing existing code:

1. Inspect the relevant files.
2. Understand the current implementation.
3. Identify the precise cause of the problem.
4. Make the smallest safe change.
5. Run relevant tests.
6. Verify that previously working features still work.

If a migration or refactor is required, explain its purpose and preserve existing data.

## Rule 2: No fake functionality

Every implemented button must perform its stated action.

Every form must validate and save its data.

Every table must read real records.

Every status badge must reflect a persisted status.

Every KPI must be calculated from actual application data.

Every filter, search field, modal, navigation item and dropdown must work.

Do not use hardcoded sample numbers as if they were live business data.

Do not create buttons that merely display an alert saying that a feature is coming soon.

If a future feature is not implemented, clearly label it as planned or unavailable.

## Rule 3: Database persistence is mandatory

Use a real relational database.

Changes must survive page refreshes, navigation, application restarts and normal redeployments.

Do not use browser localStorage or sessionStorage as the primary database.

Do not substitute hardcoded JavaScript arrays for backend records.

Do not create an elaborate frontend before establishing the database and server-side operations.

## Rule 4: Keep every phase functional

Implement the product incrementally.

After each phase:

- Run the application.
- Test all relevant CRUD operations.
- Verify database persistence.
- Test important relationships.
- Inspect application logs.
- Fix errors introduced by the current phase.
- Confirm that existing functionality remains intact.
- Document what works and what remains incomplete.

Do not proceed to the next phase while critical errors in the current phase remain unresolved.

## Rule 5: Preserve project state

Maintain:

- A project implementation checklist.
- A feature status register.
- Database migration history.
- A list of known bugs.
- A list of incomplete integrations.
- A short technical progress log.
- A list of verified acceptance tests.

Update these after meaningful implementation milestones.

Do not claim a feature is complete unless it has been implemented and tested.

## Rule 6: No destructive shortcuts

Never run destructive database commands, drop tables, overwrite production data or reset migrations merely to make an error disappear.

Use versioned migrations, backups and explicit recovery procedures.

Never overwrite user-created work without first understanding the impact.
